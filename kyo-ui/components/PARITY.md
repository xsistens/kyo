# Feature parity: kyo-ui-components against PrimeReact

The reference API surface is **PrimeReact v10.9.x**, the richest stable documented surface, with v11 naming cleanups where they simplify. The pixel reference is **PrimeVue 4** under the same `@primeuix` presets the generated tokens and component CSS come from, so a rendered control can be compared against the reference computed style by style.

This file is the record of what is deliberately **absent**. Every entry is a feature the reference has and this library does not, with the reason. Nothing here degrades silently: a deferred feature is missing outright rather than half-present, so a caller who reaches for it fails to compile rather than getting a broken approximation.

Two conventions keep it honest:

- **A component's scaladoc wins.** It sits next to the code and moves with it; this file is the cross-component overview. Where the two disagree, the scaladoc is the fact and this file is the bug.
- **No counts are restated here.** The component count and the two glyph-set sizes are pinned by `NodeTest` and `IconsTest` and quoted from there; a number repeated in prose drifts from the thing it counts.

## Coverage

Every PrimeReact component is implemented except one, and every feature row of every implemented component is adopted except the rows listed below.

**The exception is `Editor`.** Prime's editor wraps Quill, a full rich-text editing engine with its own document model, toolbar and selection handling. Nothing in it survives the translation to a server-rendered value, so it is out of scope rather than approximated.

The interactive demo, one page per component and one section per feature, lives in the separate `kyo-ui-components` repository, which consumes this module as a published artifact. Deferred features appear there as "Not yet implemented".

## Deferred features, per component

| Component | Deferred | Notes |
|---|---|---|
| Overlay | portal | Flip and shift are implemented and re-measure continuously: the panel measures itself on open and on every scroll or resize, then repositions in place through an attribute patch instead of a re-render, so the vertical flip and the horizontal shift track the viewport live. `autoFlip(true)` is the default and lifts every overlay consumer. The host-gated menu-family submenus keep their declared anchor (one subscription per ref chain, unmeasured). Without a portal the panels stay in the anchor subtree, so no ancestor may carry a `transform`. Escape dismisses one level at a time. |
| Select | editable mode, per-option templates, virtual scrolling | The editable value model is not modelled yet. The panel's keyboard lives on whatever holds focus (the trigger, or the filter header's input), so the opening key lands ON an option, the selected one or the first pickable, and Tab in either direction closes the panel rather than leaving it open behind the reader. Where the option list is long enough to scroll, Chromium makes that scroll container a tab stop of its own, so a Tab out of the filter header lands there, and the close then returns focus to the trigger: a second Tab leaves. |
| AutoComplete | multiple selection (chips), `forceSelection`, virtual scrolling | Clicking back into the input closes the panel first, which is the backdrop's doing. Tab closes the panel, like Escape: the field the Tab is leaving is where the panel's keyboard lives. |
| DatePicker | locale and `dateFormat` parsing, automatic today highlight, seconds, `numberOfMonths`, disabled dates | Render is pure and cannot read a clock, so `today(iso)` is an explicit parameter and the ISO-only value model is deliberate. Backdrop dismissal writes the open ref directly and so bypasses `onClose`. The keyboard rolls the ARIA date-grid pattern rather than Prime's per-day roving tabindex: the grid is one tab stop with an announced highlight, since a day here is a `span` and not a control. Beyond Prime: opening puts the reader in that grid whichever way the panel was opened, so the field does not hold the caret while the panel is up; Ctrl or Cmd turns an arrow into a page (a month sideways, a year upward, times four and times ten with Shift); and Escape is a cancel rather than a plain close, putting back what the panel held before the reader changed anything in it, without firing `onChange` for the undo. |
| Tooltip | `showDelay`, `hideDelay`, `autoHide(false)`, mouse tracking, viewport flip | Driven by CSS `:hover` and `:focus-within` rather than Prime's JS tooltip: no state, no round-trips. The box is not interactive. |
| Popover | `showCloseIcon` | The arrow sits at a fixed token offset; Prime tracks the pointer with JS. Overlay's limits apply. |
| Menu family | hover-open (root and nested rows open on click), mobile and hamburger modes, per-item templates, typeahead | A round-trip per hover is disproportionate for a server-rendered menu, so the hover styling stays in the sheet and the opening is a click. Escape and outside click each dismiss one level; Tab dismisses every level at once, since it carries the reader out of the widget rather than one step up it. The highlighted row is announced through `aria-activedescendant` off an id the component mints, so a menu the page never named still says what it has highlighted. |
| SpeedDial | circle, semi-circle and quarter-circle types; the mask variant; the fan transition; outside-click dismissal | The non-linear types need JS-measured per-item offsets, and the fan restarts on every re-render because kyo replaces the subtree. It is not an Overlay, so nothing watches the page for a click outside it; the keyboard closes it with Escape or with the Tab that carries the reader out of the menu. Prime leaves every hidden action a tab stop and gives the fan no keys at all; kyo renders a closed fan empty, makes the dial one tab stop (the toggle), and operates the open fan as the `role="menu"` it declares. |
| MultiSelect | virtual scrolling, per-option templates, `selectionLimit`, loading state | Select-all is binary because PrimeVue 4 renders no indeterminate select-all, and it counts across every group because Prime has no per-group select-all. Labels join in option order, since a `Set` carries no pick order. Opening lands on the first selected option, or the first pickable one. Two deviations from Prime, both because the panel's keyboard lives outside it: Tab closes the panel instead of stepping into the header, and the select-all box is therefore no tab stop, reached from the keyboard by Ctrl or Cmd with A (the ARIA listbox chord) and by the pointer as before. |
| CascadeSelect | mobile query mode, option templates, `showClear`, loading state | The arrows walk the whole nested chain through MenuNav. No panel seeds focus: it stays on the trigger, which is the combobox and carries the announcement. Opening lands on the first root option, not on the selected leaf, which the closed chain gives no row on the screen; Tab closes every open panel at once. |
| TreeSelect | chip display mode, the header filter, `showClear` | Checkbox mode inherits Tree's cascading tri-state. The trigger keeps focus and wears the hosted tree's own keyboard, so the tree inside the panel is not a second focus owner. Opening lands on the first selected row that is on the screen, or the first row; Tab closes the panel. |
| Drawer | non-modal (mask-less) mode | The slide animation is implemented per docking edge, and the panel slides back out on the mask's leave ghost. The mask sits on the Dialog z-layer, which is what a mask-less mode would have to leave behind. |
| Dialog | the user-driven maximize toggle button, positioned dialogs (top, bottom-left and the rest) | Draggable and resizable are implemented: a stable header drag surface plus a corner resize handle. A movable dialog drops the open scale animation, which would otherwise replay on every drag frame. Enter and leave animations are implemented. |
| Toast | swipe dismiss | Enter and leave animations are implemented for the single Toast and for the ToastService region, sliding per screen position. Swipe dismiss needs pointer-drag on the message itself. |
| ToastService | per-session stores over server push (one instance is shared across sessions), `Env.get` inside a handler over server push | Providing the layer at the root is the doctrine, and kyo-http session fibers do not inherit the `runHandlers` caller's context, so the service is resolved at build time. |
| ContextMenu | pointer-position anchoring, global and document mode | The panel anchors to the target region rather than the pointer, because kyo's `MouseEvent` carries no coordinates. The native context menu is suppressed inside the region. |
| ConfirmDialog | the imperative service form (a confirmation service resolving the choice through `Env`), the ConfirmPopup variant | The declarative ref plus `onAccept` and `onReject` covers the anatomy and the interactions. Every dismissal, Escape included, counts as a reject. |
| DataTable | (none) | Every feature row of Prime's DataTable page is implemented; what follows is where this one differs from Prime in HOW, which the file's other rows carry beside their deferrals. The header and footer slots, per-column footers in a real `tfoot`, the loading mask, a scrollable height with pinned row groups, and the checkbox column's select-all header are implemented. Select-all is binary, as in Prime, and covers every row that survived the global filter rather than the visible page. Prime's `stateKey`/`stateStorage` is `state` and `restore`, minus the storage. Prime persists sort, filters, page, selection, widths, order and expansion itself because in Prime that state lives inside the component and a caller has no other way to reach it; here every one of them is already a ref the caller bound, so `state` bundles them into a `TableState` and `restore` writes them back, and where the value is kept between visits stays the application's, which is the only place that knows whether it belongs in a cookie, a URL, a profile row or nowhere. A field whose ref is not bound reads as its default and is not restored, and nothing is validated on the way in, because a restored spec naming a column the table no longer has, a width for one it never had and a page past the end are each already reported or clamped at render. Export is `csv`, in two forms: `csv(rows)` is pure and takes the rows to write, which makes an export of the selection one line, and `csv` on its own reads the bound sort and filters and gives back the rows as the reader is looking at them, across every page rather than the one on the screen, which is what Prime's `exportCSV()` exports too. Both go through the same arrangement the body renders, so the two cannot answer differently. A column's heading is `exportHeader` or its header, its field is `exportAs` or its text projection, and `exportable(false)` leaves it out; `exportAs` is Prime's table-wide `exportFunction` put on the column the way the rest of that class is, and it is what a column rendering only a `body` needs, since a cell's content is a `UI` and there is no honest way to read a string out of one. Fields are quoted the way RFC 4180 asks and `csvSeparator` decides what counts, the columns come out in the reader's own order, and a column `visible` is hiding still exports, since visibility is about the screen and `exportable` about the export. Where Prime's `exportCSV()` also triggers the download, this stops at the string: getting bytes to a reader is an anchor over a `data:` URL (kyo-ui's `a.download`, added for this), an endpoint, or a file the server writes, and a component that owned that choice would be owning where the bytes go. The row a right-click landed on is `contextMenuRow(ref)`, Prime's `contextMenuSelection`: it marks that row with Prime's own class, which is a second mark separate from the selection, and suppresses the browser's menu over the rows. The panel is `ContextMenu`, which wraps the table rather than being a prop on it, so the ref is the caller's to clear when the menu closes: the table cannot see a panel it does not render. Cells are picked through `selectedCells(ref)`, Prime's `cellSelection`, bound as a `Set[CellPath]`: a cell has no identity until a row key is paired with a column path, so it is a second binding rather than a mode over the row one, and `selectionMode` still says whether a click replaces or toggles. One click can mean one thing, so binding more than one of cell editing, row selection and cell selection is a card, with editing keeping the click. A selected cell is the one place the extracted sheet carries a token (`--p-datatable-body-cell-selected-border-color`) and no rule that reaches a cell, since Prime's own selected rule stops at the `tr`: the class is a documented `.p-uic-*` one and its colors are Prime's, so a theme that recolors a selected row recolors a selected cell with it. Prime's `isDataSelectable` is `selectableWhen`, and it closes every path into the selection rather than one of them: a rejected row takes no selecting click, loses the pointer that offers one, renders its checkbox with Prime's disabled class and no handler at all, and is passed over by select-all. The predicate is read where the selection is written and not once at render, so a row cannot stay selected on the strength of having been selectable earlier. Over a table with no `selectionMode` it limits nothing and says so in a card. Prime's `rowClassName` is `rowClasses`, taking the list a class attribute already is rather than Prime's string or class-to-condition object, so a condition is the caller's own `if`; they append after the table's own classes, and a cell is styled through `Column.body`, which is any UI. Multi-sort follows Prime: Ctrl or Cmd to add a key, ranked with Prime's sort badge. A plain click cycles the only sorted column through all three states, but merely reverses one of several, so a multi-key spec cannot lose a key to one click too many. It deviates in one way, deliberately: `SortDirection` has an `Unsorted` case, so a column switched off keeps its slot in the priority order and the next click restores its rank instead of appending it behind the others. `removableSort(false)` leaves Prime's two-state cycle. `Column.sortable` is a second axis Prime does not have, taking a `Boolean` or a `Signal[Boolean]`: `sortBy` says how a column sorts, `sortable` whether the reader may change it, so a column can be sorted by the spec while its header is inert. It drops the affordance and keeps the state, since the rows really are sorted that way, and one rule keeps it honest against the click transitions: a click clears only the entries the reader could have cleared themselves, so a plain click on a free column no longer collapses a locked entry with the rest of the spec, the trailing-`Unsorted` pruning stops at one, and "several columns sort" counts the entries the reader can act on. The same protection covers a spec entry naming no column of the table. Row grouping goes past Prime's, which takes one field and one mode for the whole table: `groupBy` takes a nested level per argument, each carrying its own header row, summary row and visibility, and `expandedGroups` keys collapse state by `GroupPath` so the same key under two parents collapses independently. A level's key is of any type and labels itself through `toString`, which is also its identity. Prime's rowspan mode becomes `Column.rowSpan`, a marker on the column rather than a name pointing at one, merging by the column's own text projection unless given a key, which may be any type strict equality will compare since it is never rendered, whose runs are clipped by the merged columns left of it and by the innermost group, which is what keeps two spans from crossing. `Column` carries a phantom kind, so the two options a hierarchy cannot honor, `footer` and `rowSpan`, make a column `FlatOnly` and `TreeTable.columns` refuses it at compile time instead of dropping it at render. Column grouping goes past Prime's the same way. Prime's ColumnGroup is a second, parallel structure: header cells authored beside the column list, each carrying its own `colSpan` and `rowSpan`, so a column added to one and not the other renders a header and a body that disagree at every row, silently. Here a `headerGroup` wraps the columns it spans, nesting as deep as it needs to, and both spans are read off that tree, which leaves nothing to keep in step. A group is a label and nothing else, so sorting, footers, filtering and merging stay on the leaves. The footer group is derived from the leaves rather than separately authored, which is the one place Prime is more expressive: an arbitrary footer row shape has no counterpart here. The sort spec addresses a column by its PATH, the labels of the groups around it followed by its own header, carried as a list of parts so no separator becomes API: a column in no group keeps a one-part path, which is its header, so every spec predating groups is unchanged, and one header under two groups is still two columns. Two authoring mistakes no type can catch are named in a `.p-uic-key-error` card instead, a group holding no column and a spec entry matching no sortable column, the latter covering a mistyped part, a missing `sortBy`, and a path missing the groups above it. The group header and footer rows are template slots in Prime, so the extracted sheet carries no rules for them and two documented `.p-uic-*` rules give them their weight and ground, as with the empty-message and expansion rows. Editing goes past Prime's, and past AG Grid's, by putting the whole round trip on the column: `Column.editable(read)(write)` says where a cell's value comes from and where an edited one goes, and the `CellType` in scope carries the editor, the formatter and the parser between them, so an editor and a parser that disagree about the string domain cannot be written. Prime and AG Grid both bind the editor per column and the value round trip somewhere else (a template slot there, `valueParser`/`valueSetter` on the colDef here), which leaves the caller to say which column an edit belongs to and to own a draft per column; here the table seeds the draft from `read`, the editor writes into it, and the commit goes back through `write`. `editingCell` binds one `CellPath`, `editingRows` a set of row keys plus Prime's editor-button column, Enter commits and Escape discards in both. Where a commit lands is a second binding: `rows(ref)` lets the table store the new row itself, the plain `rows(Seq)` hands it to `onCellValueChanged` instead, and a column that is editable while the table can do neither is a card, since the commit would be computed and dropped. Rules are `form.Validator` over the PARSED value, so a refused commit carries a `FieldError` and shows its message under the editor, which is the one thing AG Grid's `valueSetter` cannot do: a `false` there means both invalid and unchanged, with no channel for a message. A table that binds an editing state renders through a mount, since the drafts and the standing error are state no caller supplies; the static projection is the same table with its editors closed and its affordances inert. Every gesture that LEAVES an open cell commits it: Enter, Tab, and moving the editor to another cell, each of them stopping where it is when the commit is refused, so the value being fixed keeps the reader. Two of Prime's triggers are deferred: cell editing does not commit on blur or on a click outside the table, because a `td`'s blur fires the moment focus moves into the editor, and an outside click is only observable through a backdrop, which over a table would swallow the reader's next click. An editor left open that way keeps what was typed in it; nothing is dropped, it is simply not written until the reader says so. Keyboard navigation ships with it, over a cursor that is the focused `td` and not a ref, so an arrow costs one focus command and no re-render: arrows, Home/End (ctrl for the grid's ends), the Page keys, Enter and F2 to open, any printable key to open ON that character, Space to select the row, Escape to close. Tab is the interesting one, and it needs no interception: the tab stops are exactly the editable cells and the DOM is row-major, so the browser's own order already IS the next editable cell wrapping into the next row, and the handler only agrees with it by committing what Tab left and opening what it arrived at. That matters because a kyo handler is async and cannot decline a browser default in time, which is also why the arrows are suppressed declaratively (`preventScrollKeys`) rather than by a handler. An editor that closes hands focus back to its cell, since the editor is the focused element while it is open and the cursor would otherwise die on the first commit; not after Tab, where the browser moves focus itself, and not after a refused commit. A row closed by its button lands on the row's first editable cell rather than on the button that replaced the pressed one, because that element is new and a self-command resolves its id before the insert. `Column.navigable(false)` is `suppressNavigable`: stepped over by the arrows, never a tab stop, untouched by the mouse. `cellNavigation` defaults to on once a column is editable and turns it all off; a table that opts out renders the markup and tab order it rendered before. Deferred with the rest: `suppressKeyboardEvent`, the arrow that moves up into the header, Excel's Enter-moves-down pair, and full-row Tab semantics. Prime renders the row editor through a template slot, so the extracted sheet carries no rules for it and three documented `.p-uic-*` rules keep the save and cancel buttons a pair, let an open editor fill its cell, and colour a refused commit. Which columns show is `Column.visible`, taking a `Boolean` or a `Signal[Boolean]`, where Prime's toggle is a separate MultiSelect component driving a list of column definitions: a hidden column contributes no header, body or footer cell, the colspans follow, and a `headerGroup` whose columns are all hidden goes with them, while a group authored with no column at all stays and keeps reporting itself. It hides the column without taking it out of the table, so the sort spec still sorts by it and hiding one never reshuffles the rows; the global filter goes the other way and searches only what is on the screen, as AG Grid's quick filter does. The keyboard grid renumbers with the header, since the cursor addresses cells by position. Per-column filtering is `Column.filterBy` plus `columnFilters(ref)`, rendering Prime's row display: an inline filter per column, the mode menu behind the funnel beside it. Where Prime picks the constraint list from a `dataType` string and AG Grid from a filter component name (`agTextColumnFilter`, `agNumberColumnFilter`), it is the column's `CellType` that decides here: a type carrying an ordering is compared and reads the query as a VALUE, everything else is matched as text over what the type formats it as, so a number column answers `< 50` where a text match would put 100 before 50. A query the column cannot read marks its own input and filters nothing, rather than emptying the table behind a typo, and a mode the column never offered is refused the same way. A hidden column does not filter, as the global query does not search it. Prime's menu display is `filterDisplay(FilterDisplay.Menu)`: a funnel in each filterable header cell over Prime's filter popover, holding several conditions on one column joined by Match All or Match Any, with the buttons to add, remove, clear and apply them. A `ColumnFilter` is a list of `FilterRule` and an operator for that reason, and `ColumnFilter(query, mode)` is the single rule a row display holds; a seeded filter carrying more under a row display shows the first and says so. The menu edits a DRAFT and applies it on the button, which is the one behavioural difference between the displays and the reason Prime has the button: a table is not re-filtered on the way to the second condition. One condition the column cannot read makes the WHOLE filter unusable rather than being dropped from the join, since a condition silently ignored would widen the result under Match Any and narrow it under Match All. Prime's own filter elements per column, and a filter over a hierarchy, which needs a matching row to keep its parents, stay deferred; a `TreeTable` refuses a filtered column at compile time rather than dropping it at render. How wide a column is is `Column.width`, and `columnWidths(ref)` hands it to the reader, keyed by the same path the sort spec and the column filters use. The width reaches the column through a `colgroup`, which Prime renders only for a scrollable table and which is the only structure that can carry one: a width on a cell sizes the row it is in, and a grouped header's cell spans several columns and cannot name a width for any of them, so the two would disagree exactly where Prime's own ColumnGroup already does. It goes past Prime's in the same way `sortable` does, by being a per-column axis where Prime has a table-level flag: `resizableColumns` is all or nothing there, and here a single column pins itself with `resizable(false)`. What a drag moves is a BOUNDARY and not a column: the pair it sits between trades width and the total is preserved, which is Prime's `fit` mode, so the table never outgrows the space it was given, and the widths are measured on the grab rather than read out of the map, so a column the caller never sized is as draggable as one that was. A boundary needs a resizable column on both sides of it, and the last column has none, which is the rule Prime states in CSS by hiding the last resizer in fit mode. It resizes LIVE rather than on release, as the resizable Dialog does, so Prime's `.p-datatable-column-resize-indicator` has nothing left to indicate and is not rendered; the cost is one re-render per animation frame of a drag, which is what the client's own rAF coalescing already bounds it to. `columnResizeMode(Expand)` is Prime's second mode, and it moves one COLUMN rather than the boundary beside it: only the grabbed one changes, the table grows by the same amount and scrolls sideways, and the last column becomes draggable since it no longer needs a neighbour to trade with, which is exactly what Prime's `.p-datatable-resizable-table-fit` rule says by hiding that last handle. It costs the one thing fitting does not need: the table has to state its own width or the browser hands what the columns leave over back to them, so `Expand` needs every visible column to have a width and the table renders their sum, with the checkbox, expander and row-editor columns carried as the variables they are sized by. A column without one is named in a card and the table resizes to fit instead, which needs no widths at all. Prime reaches the same end by measuring the header on the grab and pinning every column in JavaScript. The extracted sheet carries the clipping that belongs with an authoritative width and not the layout algorithm it belongs to, so one documented `.p-uic-*` rule supplies it. Which columns the reader keeps in sight is `Column.frozen`, taking Prime's two edges as `FrozenEdge.Start` and `End` where Prime carries them as a boolean plus an `alignFrozen` string. Declaring one puts the table in a scroll container by itself, since a column can only be frozen against something that moves and `scrollHeight` only ever answered the vertical half of that question. A frozen cell holds at the distance the columns between it and its edge take up, which is where the widths earn their keep: PrimeVue computes the same two properties in JavaScript, measuring the previous cell's `offsetWidth` on every render and on every resize, and here the widths are already facts, so each offset is written once, declaratively, and follows a resize drag because both read the same bound map on the same render. Two rules come out of that arithmetic rather than out of taste: a frozen column needs a width, and the frozen ones have to reach their edge, since a free column left between them and it would carry the frozen one away as it scrolled. Breaking either freezes nothing at all and names the column in a card, which is the same trade the filter row makes with a query it cannot read: an offset summed over a width that is not there parks a column over the middle of the table, and a column that scrolls is the smaller wrong. A header group spanning a frozen column and a free one is the third card, since one cell cannot half scroll. The checkbox, expander and row-editor columns are between a frozen column and the edge too, so they hold with it, and their width is part of the offset; Prime never has to answer this, because its selection column is a `Column` the caller marks itself. That width is a `--p-uic-dt-*` variable rather than a number, so the width the `col` is given and the width the offset counts are one quantity, and the three of them are also what the fixed layout needed all along: under it a column with no width takes an equal share of what the sized ones leave over, which over a checkbox is far more than a checkbox can use. Prime never meets that either, since it renders a `colgroup` only for a scrollable table and lets the browser size those columns by their content everywhere else. Where the columns are is `columnOrder(ref)`, a list of column paths, and binding it lets the reader drag a header cell elsewhere; `Column.reorderable(false)` pins one, a per-column axis where Prime has one `reorderableColumns` flag for the table. A partial order means "these first", and what a drag writes is the whole list including the columns `Column.visible` is hiding, so hiding one and moving another does not lose the first one's place. Where a drop may land is read off the table rather than declared: a cell moves among its own SIBLINGS, since the header is a tree and one cell cannot sit in two groups, and a boundary is dropped from the list when moving there would leave a frozen column adrift or carry a pinned one along, each checked by making the move and asking the rule that already exists, so the offer and the diagnostic cannot disagree. That is also where it goes past Prime twice: a header group drags as one unit, where PrimeVue turns reordering off entirely once a ColumnGroup is present, and a group whose columns an order asks for apart is named in a card and rendered whole rather than torn. The gesture is pointer-driven, since kyo-ui has no HTML5 drag-and-drop and does not need one: a press that never travels stays the click that sorts, and the click a real drag leaves behind is swallowed by whichever header cell it lands on, which after the drop is no longer the one that was grabbed. The line showing where the column would land is a border on the cell beside it, where Prime positions two floating arrows measured in JavaScript on every move; the state is written only when the answer changes, so a drag re-renders once per boundary crossed rather than once per frame. ROWS reorder the same way, through `reorderableRows(true)`, which adds Prime's grip column at the leading edge where Prime has the caller place a `rowReorder` column of their own. What a drop rewrites is the row list, so it writes into a bound `rows(ref)` or goes out through `onRowReorder`, with both indices counted in the list and not in the page, and a table that can do neither is a card. It also needs the rows on the screen to BE the rows in the list, in that order, so while a sort spec, a filter or a grouping decides the order, over a lazily loaded window where the order is the query's, or over a windowed body, the grips render without a drag and a card names which of them it is; paging is fine, since a page is a contiguous slice. The geometry is measured once on the grab and in ONE round trip for the whole page, through kyo-ui's batched `requestMeasureByIds`, because moving a row changes no height: the rows the reader picked up from are the rows they let go over. Prime learns the same thing from HTML5 drag events, which kyo-ui does not have; a kyo drag is pointer-driven and captured by the element the press landed on, so the rows the pointer travels over never hear about it. Rows the table did not prepare are `lazyRows(total)`, Prime's `lazy` and `totalRecords` in one setter, since locally the total IS the row count and a table handed one has been handed something it could not have worked out: it renders the rows verbatim, in the order they arrived, and paginates over the total. Prime needs an `onLazyLoad` event carrying a `DataTableLazyEvent` (first, rows, sortField, sortOrder, filters) because its sort, filter and page state live inside the component; here that state is already the caller's refs, so such an event would only hand back what the caller wrote, and a fiber observing them fetches the page they describe and stores it into the bound rows and total. One thing changes for a column: the ordering is not what sorts a prepared table, so `sortable(true)` is what marks a server-sorted one and a `sortBy` still counts with its projection unread, while the default stays no, or every column would offer a sort nobody asked for. What the table holds is also all it can name, so a select-all covers the page it was given, a `Column.footer` aggregate sums that page, and a `groupBy` run stops at its edges; Prime answers the first of those with a separate `selectAll` binding plus an `onSelectAllChange` event, which is a second state to keep in step with the first. Two mistakes it can still see it reports, more rows than one page holds and more rows than the total says exist, neither of which shows in the table itself. The other half of that is `RowSource`, which is where the fetching lives: a block cache keyed by the query, a prefetch of the neighbouring blocks, and a busy flag that stays down when a range was already buffered, bound in one call with `source(...)`. Prime has no counterpart at all, and AG Grid's is a row model INSIDE the grid (`datasource`, `cacheBlockSize`, `maxBlocksInCache`), which answers the question for one component and leaves DataView, Tree and VirtualScroller to answer it again; here it is a value beside the table, so one source can feed any of them and the table goes on rendering a window it was handed. Rows are fetched in BLOCKS and not in pages, since a viewport asks for rows 37 to 52 and that lies across any page boundary: a page is then a range that starts on a block boundary, and the block size defaults to the page size. The total is a `Total` rather than a number, so a source that cannot count says `Unknown(hasMore)` and the paginator grows a page at a time instead of counting out pages nothing will ever fill, which is what AG Grid needs a second row model for and Prime does not cover. The source fills in the floor under that length from how far it has served and never lets it fall, since a page list that shrank on the way back would be a worse lie than not knowing, and a block reporting nothing after it turns the unknown into an exact count. One rule inside is what makes the buffer safe rather than merely fast: a fetch is never interrupted, only the waiting for it, since `Signal.observe` closes its per-value scope the moment the demand changes and a fetch forked into that scope would die exactly when the reader arrives on the page it was fetching. Rows bound twice, from a source and from `rows`, are a card, since nothing in the markup says which of them was read. A table can scroll instead of paginating: `scrollRows(itemSize)` beside a `scrollHeight` renders the rows in view plus an overscan, in Prime's own nesting, the scroller between the table container and the table, which the extracted sheet names beside the plain one. Prime's is a `virtualScrollerOptions` object holding a component's worth of props (`itemSize`, `lazy`, `onLazyLoad`, `numToleratedItems`, `showLoader`, `loading`, `delay`); here the row height is the one number the arithmetic needs, the overscan defaults beside it, and the loading is not a flag because the demand is a ref the source already reads. What is not drawn is held by Prime's own spacer row on both sides of the window, since an empty `tr` collapses in table layout and `.p-datatable-virtualscroller-spacer` is what gives it a height, and a row keeps the stripe its own index gives it rather than its place in the window. Over a `RowSource` it holds nothing at all: the scroll writes the demand, a row that has not arrived is a row of `Skeleton` cells the same height, and how far the list reaches comes from `Total`, so infinite scrolling falls out rather than needing Prime's second mode. AG Grid answers the same question with a row model inside the grid and a second one (`infinite`) for an unknown count; here one source serves the table and a `VirtualScroller` alike. Placing rows by counting them needs every row the same height, so `groupBy`, `rowExpansionTemplate` and `Column.rowSpan` each name themselves in a card and leave the table rendering every row, which is slower and right; the keyboard cursor is off for the same reason, since it addresses cells by their position among the rendered rows, and a page size a windowed table will not read is a card of its own. How that viewport is SIZED has a second answer, `flexScroll(true)`, which takes the height from the parent rather than stating one, Prime's `scrollHeight="flex"`. Prime carries the mode as a magic value in the string a length goes into; here it is its own switch, since the two are different questions and only one has an answer the table can read before layout, which is also what the mode costs: `scrollRows` cannot window against it and says so, while `frozenRows` holds against it, because holding needs a scroll container and not a number. Given both, the stated length is what the table scrolls and the flag is a card. Frozen ROWS are `frozenRows(rs)`, Prime's `frozenValue`, rendered as Prime's second `tbody` carrying both the body class and the frozen one, since every body rule is keyed on the first. The extracted rule has the `position` and the `z-index` but not the `top`, which is the one quantity in this component that can be neither declared nor computed: it is whatever the header cells came out as. PrimeVue measures it once in a lifecycle hook and again on a window resize; here the header is OBSERVED (`observeViewportById`), so the offset is a signal the group renders, and a header that rewraps for any reason moves the rows with it. Until the first measurement lands the group sits at the top of the body in flow, which is where it belongs at rest, so a first paint shows no jump. They are a list of their own rather than a subset of the body's, and a row in both is a card, since one key over two rows is a selection, an expansion and a click that land twice; a table with no scroll height for them to hold against is the other. They are not in the keyboard grid, which addresses cells by their position among the SCROLLING rows. The paginator below the rows is configured through `paginator(f)`, a function over the Paginator the table renders: Prime mirrors a handful of the paginator's props onto the table (`paginatorTemplate`, `currentPageReportTemplate`, `rowsPerPageOptions`) and a caller reaching for one it did not mirror has nowhere to go, while here the paginator is a value and one name reaches every setter it has. The four the table owns are applied after `f` and cannot be overridden from there, since a paginator disagreeing with the rows above it would page a list nobody is looking at. `Paginator.template` is Prime's `paginatorTemplate` as a list of `PaginatorElement` values rather than a space-separated string, so a misspelt name does not compile where Prime's renders nothing and says nothing; the list replaces the layout rather than adding to it, and an element named with nothing behind it is a card. `JumpToPageDropdown` completes the vocabulary, which is one element Prime has and this did not. |

## Where this library goes beyond PrimeReact

- **Two-way bindings on every stateful prop.** `value`, `checked`, `selected`, `expanded`, `open`, `sort` and `page` each take a `SignalRef`, which is strictly more than a controlled prop: the component reads and writes the same value the caller owns.
- **The same behaviour over server push.** Everything above, including the pointer drags (ColorPicker, Knob, Dialog, Carousel), the measure round-trip behind the Overlay flip, and the imperative commands (InputOtp focus, Terminal scroll), round-trips over kyo-ui's WebSocket with no component JavaScript at all.
- **Self-addressing.** A reusable component mints a session-unique id, stamps it on its own element, and drives focus, scroll and measurement at it without ever learning its structural render path.
- **Typed options and rows.** `options(Seq[A])(label)` and `DataTable[A]` replace string-keyed `optionLabel` and `field` props, so a typo is a compile error rather than an empty column.
- **`invalidMessage` renders an inline message row.** Prime leaves that to the form layer.
- **Option groups reach the accessibility tree.** Prime renders a group header as a flat `li` beside the options it labels, which styles correctly and conveys nothing: the options are the header's siblings, so no relation survives into the tree. Here a group is a real `li[role=group]` carrying its label as its accessible name, holding header and options in a nested `ul[role=none]` that drops out again, which leaves every option a descendant of its group as the ARIA listbox pattern specifies. Two `.p-uic-*` rules restate the flex column and inherit its gap, so a grouped panel measures exactly like a flat one. Select, MultiSelect, AutoComplete and Listbox share the anatomy.
- **A second glyph set.** `FioriIcons` sits alongside PrimeIcons, and both emit one definition per glyph so dead-code elimination keeps unused paths out of a bundle.
